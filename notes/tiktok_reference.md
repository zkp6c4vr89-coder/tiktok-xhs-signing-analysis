# Reference analysis: notemrovsky/tiktok-reverse-engineering

Summary of the reference repository's claims, written from a complete read of its
README and source. This is a *description of someone else's work*, the baseline that
Part A sets out to reproduce independently. Every claim below is theirs until Part A
confirms or contradicts it; the "Part A check" column in
[analysis/tiktok/REPLICATION.md](../analysis/tiktok/REPLICATION.md) will track that.

- Source: https://github.com/notemrovsky/tiktok-reverse-engineering
- Pinned at commit `0f8b70460d376fdc41785a122454bd5bccb170cd` (2026-07-13), cloned to
  `samples/reference/` (git-ignored, not redistributed).
- Author's own caveat: "a 5-6 hour speedrun, so double-check everything." Several
  claims are explicitly hedged ("some opcode interpretations might be wrong").
- Note on naming: two of the author's identifiers for the string/number arrays are
  racial slurs. This project refers to them by neutral placeholders — `ARR_STR`
  (the string array, referenced in code as `Kg[...]`) and `ARR_NUM` (the number
  array, referenced as `aa[...]`) — and will not reproduce the originals anywhere
  in the public repo.

## 2. Claimed VM architecture

A classic **stack machine**, devirtualized from a deeply nested `if/else` dispatcher
into a flat `switch`. Registers/state named in the README:

- `v` — evaluation stack; `l` — stack pointer (top of `v`)
- `c` — program counter (index into the current instruction array `o`)
- `a` — scope chain; `f`, `d` — exception state (flag, value)
- `g` — call stack (saved frames pushed on CALL)

Instruction format: 1-byte opcode (0–76) followed by variable operands (immediates,
jump offsets, string/number-array indices, scope depth+index pairs).

## 3. Claimed opcode set — "77 opcodes"

The README states **77 opcodes** and gives a partial control-flow table naming:
1 JUMP_IF_FALSE, 3 JUMP, 19 TRY, 20 JUMP_IF_FALSE_OR_POP, 26 JUMP_IF_TRUE_OR_POP,
29 SWITCH_CASE, 31 JUMP_IF_TRUE.

**Discrepancy found on read (to resolve in A4).** `disasm.js`'s switch actually
implements **66** opcodes, not 77. In the range 0–75 these ten are absent:
`19, 25, 31, 46, 56, 59, 68, 69, 70, 73`. Two of them — **19 (TRY)** and
**31 (JUMP_IF_TRUE)** — are named in the README's *own* control-flow table but have
no case in the disassembler (the VM loop may handle them elsewhere, or they were
left out of the static disassembler). So "77" is the author's opcode-space estimate,
while the shipped disassembler covers 66. Part A will state the number I actually
reproduce and account for the gap. The 66 implemented opcodes decode cleanly into
these categories:

- Arithmetic/bitwise: SUB(0) ADD(41) MUL(22) DIV(67) MOD(60) NEGATE(13) XOR(12)
  OR(34) AND(63) shifts(8 >>>, 11 <<, 72 >>) TO_NUMBER(4)
- Comparison: STRICT_EQUAL(5) EQUAL(33) NOT_EQUAL(50) STRICT_NOT_EQUAL(54)
  LESS_THAN(24) GREATER_THAN(64) GREATER_EQUAL(27) LESS_EQUAL(74) IN(43) INSTANCEOF(44)
- Stack/const: PUSH_CONST(6) PUSH_STRING(37) PUSH_MAGIC_NUMBER(57) PUSH_TRUE/FALSE(61/23)
  PUSH_NULL/UNDEFINED(40/39) PUSH_FUNCTION(7) DUP(52) POP(9) NOT(38)
- Variables/scope: GET_VAR(66) SET_VAR(47) PUSH_SCOPE(21) PUSH_SCOPE_REF(55)
  GET_GLOBAL(30) TYPEOF_GLOBAL(62)
- Objects/props: GET_PROP(65) SET_PROP(16/71) GET_PROP_NAME(35) SET_GLOBAL_PROP(32)
  DEFINE_PROP(36) DELETE_PROP(17) NEW_OBJECT(49) NEW_ARRAY(51) inc/dec(18,28,42,45)
  FOR_IN_SETUP(10) FOR_IN_NEXT(15)
- Control flow: JUMP(3) JUMP_IF_FALSE(1) JUMP_IF_FALSE_OR_POP(20)
  JUMP_IF_TRUE_OR_POP(26) SWITCH_CASE(29) CALL(2) FUNCTION_BIND_APPLY(75)
  RETURN(58) THROW(48)

Full opcode table (number, mnemonic, stack effect) will be regenerated by our own
tool in `tools/vm/` and committed to `data/` as the authoritative appendix; the list
here is the reference's, transcribed for comparison.

## 4. Claimed string deobfuscation

Two array indirections hide literals: `ARR_STR` (1000+ encoded strings, accessed as
`Kg[n]`) and `ARR_NUM` (numeric constants, accessed as `aa[n]`). The pass is a Babel
`MemberExpression` visitor that, when the object is `Kg`/`aa`, replaces the lookup
with the literal value from the corresponding array (`t.valueToNode`). Example given:
`Kg[123]` → `"navigator"`, `aa[45]` → `2654435769` (note: 2654435769 = 0x9E3779B9, the
golden-ratio constant used in TEA/XXTEA-family hashing — a hint about primitives).

## 5. Claimed bytecode parser (`fetchInstructions`)

Reads a binary blob (`e.d` Uint8Array, `e.i` cursor). Confirmed primitives on read:

- `blabla(e)` — a **signed LEB128 varint** decoder (7 bits/byte, continuation bit
  0x80, sign-extends with `-1 << r` when the 0x40 bit is set and `r < 32`).
- `decodestring(e)` — a custom UTF-8-like codepoint decoder building each string.

Parse structure: read string count → decode that many strings; read function count →
for each function read [function index, strict-mode bool, exception-handler table of
4-tuples, then the bytecode instruction array]. Returns `{strings, instructions}`.
The author hardcoded the already-decompressed `Uint8Array` rather than reimplement
the (zip-like) decompression, to save time.

## 6. Claimed disassembler output

`OpHandler(instruction, strings)` walks one function's bytecode and emits annotated
pseudo-assembly with resolved stack positions and string/number constants, e.g.:

```
// 0 PUSH_STRING → stack[0] = "d41d8cd98f00b204e9800998ecf8427e"   (= MD5 of "")
// 3 SET_VAR scope[0][4] ← stack[0]
// 6 GET_VAR → stack[0] = scope[0][3]
```

`disassemble()` runs this over every function and writes `functions/vm{index}.js`.
The `d41d8cd9…` constant (MD5 of the empty string) appearing in vm103 is a strong
hint that the X-Bogus path uses **MD5**.

## 7. Claimed runtime tracing → token functions

Method: set a breakpoint on the opcode fetch (`var opcode = o[c++]`), push
`[VM] Opcode … pos … stack level …` lines into `window.thatarray`, and record which
function's instruction array is live into `window.oparrays`; then
`[...new Set(window.oparrays)]` gives the unique VM function indices touched while a
token is generated. `strData` was found from the return object
`{magic: 538969122, version: 1, dataType, strData, tspFromClient}` by breaking on it
and stepping back to see the pre-encryption input.

Claimed result — the entry VM functions for each output:

| VM function | Output |
|---|---|
| `vm249` | X-Gnarly |
| `vm103` | X-Bogus |
| `vm42`  | strData |

These are described as *entry points* of each pipeline, not the whole pipeline; the
actual return opcode varies by execution path (see `debug_asf/bogus_flow.txt`).
